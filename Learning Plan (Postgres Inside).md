### Глава 2. «Изоляция»

- **Сценарий с интервью:** В Spring-сервисе метод помечен `@Transactional(isolation = [подозрительная ссылка удалена]_COMMITTED)`. Два фоновых потока одновременно читают баланс пользователя ($100), проверяют условия бизнес-логики (баланс \(\ge\) \(60\)) и списывают по $60. К какому багу это приведет и как решить проблему без `Isolation.SERIALIZABLE`?
- **Практическое решение:** На уровне `Read Committed` возникает аномалия **Lost Update** / **Race Condition**.
    - _Решение 1:_ Атомарный SQL-запрос `UPDATE accounts SET balance = balance - 60 WHERE id = :id AND balance >= 60;`.
    - _Решение 2:_ Пессимистичная блокировка `SELECT FOR UPDATE` (в Spring Data JPA: `@Lock(LockModeType.PESSIMISTIC_WRITE)`).

### Глава 13. «Блокировки строк»

- **Сценарий с интервью:** Сервис-воркер забирает задачи из таблицы: `SELECT * FROM tasks WHERE status = 'NEW' LIMIT 10 FOR UPDATE`. При масштабировании до 10 реплик приложения воркеры начинают блокировать друг друга или вызывать `Deadlock`. Как исправить?
- **Практическое решение:** Перейти на неблокирующее получение задач через `FOR UPDATE SKIP LOCKED`:
    
    ```
    SELECT id FROM tasks
    WHERE status = 'NEW'
    ORDER BY created_at
    LIMIT 10
    FOR UPDATE SKIP LOCKED;
    ```
    
    Это позволяет каждому воркеру мгновенно пропускать уже заблокированные другими сервисами строки и работать параллельно без простоя и взаимных блокировок.

### Глава 16. «Этапы выполнения запросов»

- **Сценарий с интервью:** Приложение использует `PreparedStatement` в JDBC/Hibernate. Первые 5 вызовов метода работают быстро, а начиная с 6-го время выполнения запроса резко вырастает в десятки раз. В чем причина со стороны оптимизатора PostgreSQL?
- **Практическое решение:** После 5 вызовов драйвер/СУБД переключается с **Custom Plan** (план, построенный под конкретное значение параметра) на **Generic Plan** (общий план под `$1`). Если распределение данных в столбце неравномерно (высокая селективность для одних значений и низкая для других), общий план может выбрать `Seq Scan` вместо `Index Scan`.

### Глава 20. «Индексное сканирование»

- **Сценарий с интервью:** Вы добавили покрывающий индекс `CREATE INDEX idx ON orders (user_id) INCLUDE (total_amount)`. В отчете `EXPLAIN (ANALYZE, BUFFERS)` виден `Index Only Scan`, но показатель `Heap Fetches` положителен и равен тысячам обращений. Почему СУБД все равно ходит в таблицу?
- **Практическое решение:** `Index Only Scan` не требует обращения к таблице (`Heap Fetches = 0`) только в том случае, если карта видимости (**Visibility Map**) подтверждает, что все версии строк на соответствующей странице являются видимыми для всех транзакций. Если таблица недавно интенсивно обновлялась и `VACUUM` еще не успел обновить карту видимости, СУБД вынуждена читать страницы таблицы для проверки видимости версий строк.

### Глава 6. «Очистка и автоочистка»

- **Сценарий с интервью:** В Java-сервисе поток открыл транзакцию `BEGIN`, выполнил `SELECT` и «завис» в состоянии `idle in transaction` на 8 часов. Чем это опасно для базы данных, если этот поток ничего не изеняет в БД?
- **Практическое решение:** Открытая транзакция удерживает **горизонт базы данных** (`backend_xmin`). Процесс `autovacuum` не может вычищать мертвые версии строк (`dead tuples`), созданные **после** начала этой транзакции, ни в одной таблице БД. Это приводит к разрастанию таблиц и индексов (**bloat**), деградации кэша и падению производительности всей СУБД.
