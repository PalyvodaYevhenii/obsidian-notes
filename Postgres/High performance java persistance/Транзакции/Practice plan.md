## 📌 Раздел 1. Транзакции и уровни изоляции (Глава 7)

### 🔹 Блок A: Базовые уровни изоляции и аномалии чтения
- [ ] **1. Dirty Read в Read Uncommitted** #transactions #isolation
  - **Суть:** В таблице `Account(id=1, balance=100)`. Транзакция 1 меняет баланс на `500`, спит 300 мс и делает `ROLLBACK`. Транзакция 2 на уровне `READ_UNCOMMITTED` читает баланс во время паузы.
  - **Проверка:** Транзакция 2 увидела `500` (грязные данные), хотя после отката в БД остался `100`.
- [ ] **2. Read Committed: Защита от Dirty Read и снимок на запрос** #transactions #isolation
  - **Суть:** Повторить сценарий 1, но для Транзакции 2 выставить `READ_COMMITTED`. Во время паузы Транзакции 1 первый `SELECT` должен вернуть `100`. После `COMMIT` Транзакции 1 второй `SELECT` возвращает `500`.
  - **Проверка:** Убедиться, что грязные данные не видны, а снимок перечитывается на каждый запрос.
- [ ] **3. Non-Repeatable Read и кэш первого уровня (L1)** #hibernate #persistence-context
  - **Суть:** В одной транзакции выполнить `find(Product.class, 1L)`. Параллельный поток в отдельной транзакции меняет имя и коммитит. Повторить `find()`, затем выполнить нативный SQL `SELECT name FROM product WHERE id = 1`.
  - **Проверка:** `find()` возвращает неизмененный объект из L1-кеша (*Application-level Repeatable Read*), а нативный SQL возвращает уже новое значение из БД.
- [ ] **4. Write Skew (Перекос записи) в Repeatable Read** #transactions #anomalies
  - **Суть:** Таблица дежурных врачей: `Doctor(Alice, onCall=true)` и `Doctor(Bob, onCall=true)`. Инвариант: минимум один врач на дежурстве. Обе транзакции параллельно на `REPEATABLE_READ` проверяют `COUNT(*) WHERE onCall = true` (видят 2) и снимают дежурство.
  - **Проверка:** После коммита дежурных врачей стало `0` (инвариант нарушен). Проверить фикс через `SERIALIZABLE` (SSI) и `PESSIMISTIC_WRITE`.

### 🔹 Блок B: Потерянные обновления и блокировки
- [x] **5. Воспроизведение аномалии Lost Update** #concurrency #lost-update
  - **Суть:** Товар с `quantity = 10`. Поток 1 списывает 2, Поток 2 списывает 3 (с задержкой 100 мс между чтением и записью).
  - **Проверка:** В базе остается `8` или `7` вместо `5` (один поток перезаписал изменения другого без исключений).
- [x] **6. Optimistic Locking через `@Version`** #jpa #optimistic-lock
  - **Суть:** Добавить к сущности поле `@Version private Long version;` и повторить сценарий параллельного списания из задачи 5.
  - **Проверка:** Ровно одна транзакция проходит, а вторая выбрасывает `OptimisticLockException` из-за `update count == 0`.
- [x] **7. Versionless Optimistic Locking** #hibernate #legacy
  - **Суть:** Разметить сущность без `@Version` аннотациями `@OptimisticLocking(type = OptimisticLockType.DIRTY)` и `@DynamicUpdate`.
  - **Проверка:** В логах SQL старое значение изменяемой колонки подставляется в `WHERE`: `UPDATE ... WHERE id = ? AND balance = ?`.
- [x] **8. Explicit Optimistic Locking: `OPTIMISTIC_FORCE_INCREMENT`** #jpa #locking
  - **Суть:** Родитель `Order` с `@Version` и дочерний элемент `OrderItem`. При добавлении позиции вызвать `entityManager.lock(order, LockModeType.OPTIMISTIC_FORCE_INCREMENT)`.
  - **Проверка:** Версия родителя `Order` принудительно увеличивается в БД, предотвращая параллельные конфликты.
- [x] **9. Пессимистическая блокировка (`PESSIMISTIC_WRITE`)** #jpa #pessimistic-lock
  - **Суть:** Метод репозитория с аннотацией `@Lock(LockModeType.PESSIMISTIC_WRITE)`. Два потока параллельно списывают средства.
  - **Проверка:** Генерация `SELECT ... FOR UPDATE` в логах. Потоки выполняются строго последовательно, баланс сходится идеально.
- [x] **10. Deadlock (Взаимная блокировка) и упорядочивание ресурсов** #concurrency #deadlock
  - **Суть:** Поток 1 блокирует запись A, затем пытается захватить B. Поток 2 блокирует запись B, затем пытается захватить A.
  - **Проверка:** СУБД фиксирует дедлок и отменяет одну транзакцию (`CannotAcquireLockException`). Добавить детерминированную сортировку по ID (`idA &lt; idB`) для гарантированного устранения дедлока.
- [ ] **11. Высокопроизводительная очередь: `SKIP LOCKED` и `NOWAIT`** #postgres #queue
  - **Суть:** Очередь задач со статусом `PENDING`. Запрос выборки следующей задачи с `@Lock(LockModeType.PESSIMISTIC_WRITE)` и таймаутом `-2` (`SKIP LOCKED`). Запуск 5 воркеров.
  - **Проверка:** Каждый воркер мгновенно забирает свою уникальную задачу без пауз на ожидание заблокированных строк.

### 🔹 Блок C: Границы транзакций и архитектура
- [ ] **12. Физические границы транзакций: изоляция аудита через `REQUIRES_NEW`** #spring #propagation
  - **Суть:** Метод `PaymentService.processPayment()` вызывает `AuditService.logAttempt()` с `@Transactional(propagation = Propagation.REQUIRES_NEW)`. В основном сервисе выбрасывается исключение.
  - **Проверка:** Транзакция платежа откатилась, а строка аудита зафиксирована в БД.

## 📌 Раздел 2. Кеширование (Главы 5, 8, 9, 11)

### 🔹 Блок D: Statement Caching и L1 Cache
- [ ] **13. Client-Side Statement Cache в JDBC-драйвере** #jdbc #performance
  - **Суть:** Включить кеширование `PreparedStatement` в пуле HikariCP/драйвере (для MySQL: `cachePrepStmts=true&amp;prepStmtCacheSize=250`).
  - **Проверка:** Замерить время многократного выполнения параметризованного запроса по сравнению с некешированным соединением.
- [ ] **14. Раздувание L1-кеша и пакетная обработка (Batching)** #hibernate #memory
  - **Суть:** Сохранить 50 000 сущностей в одной транзакции без вызова очистки контекста.
  - **Проверка:** Увидеть деградацию времени по мере работы dirty checking и рост `Heap Memory`. Добавить периодический `flush()` и `clear()` через каждые N записей (batch size).

### 🔹 Блок E: L2 Cache, Стратегии параллелизма и Query Cache
- [ ] **15. Подключение L2-кеша сущностей** #hibernate #l2-cache
  - **Суть:** Подключить провайдер кеша (Ehcache/Caffeine) и разметить сущность аннотацией `@Cacheable`.
  - **Проверка:** В двух последовательных независимых транзакциях выполнить `find(Product.class, 1L)`. Убедиться, что во второй транзакции SQL-запрос `SELECT` в базу не отправляется.
- [ ] **16. Стратегия `READ_WRITE` и Soft Locks в L2-кеше** #hibernate #concurrency
  - **Суть:** Настроить `@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)`.
  - **Проверка:** Поток 1 открывает транзакцию и меняет сущность (кладется soft lock в кеш). Убедиться, что параллельный Поток 2 в это время читает свежие данные напрямую из БД, а не берет устаревший снимок из кеша.
- [ ] **17. Инвалидация Query Cache** #hibernate #query-cache
  - **Суть:** Включить кеш запросов (`hibernate.cache.use_query_cache=true`). Выполнить кешированный HQL-запрос дважды (второй берется из кеша). Затем выполнить `INSERT` новой записи в эту таблицу и повторить запрос.
  - **Проверка:** По логам и статистике (`hibernate.generate_statistics=true`) зафиксировать `queryCacheHit` на втором шаге и полный сброс кеша (`queryCacheMiss`) после вставки.
- [ ] **18. Кеширование по бизнес-ключу (`@NaturalIdCache`)** #hibernate #natural-id
  - **Суть:** Разметить уникальное поле (например, `slug` или `isbn`) аннотациями `@NaturalId` и `@NaturalIdCache`.
  - **Проверка:** Выполнить поиск через `session.bySimpleNaturalId(Book.class).load("ISBN-123")` дважды. Убедиться, что второй вызов резолвит ID и саму сущность напрямую из кеша без SQL `SELECT`.
