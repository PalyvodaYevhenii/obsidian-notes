**Транзакции уровня приложения (Application-Level Transactions)** — это логические бизнес-транзакции, которые охватывают **несколько последовательных веб-запросов** (включая время на размышление пользователя — _user think time_), из-за чего их часто называют «длинным разговором» (_long conversation_).

---

### **1. Почему недостаточно обычных транзакций БД?**

- **Ограничение физических транзакций:** В веб-приложении нельзя открыть одну физическую транзакцию базы данных и удерживать её открытой на протяжении всех шагов и действий пользователя. Удержание физических блокировок или поддержание графа версий в MVCC во время размышлений пользователя парализует параллелизм, исчерпывает пул подключений и резко снижает масштабируемость системы.
- **Необходимость разделения:** Физические транзакции базы данных в высоконагруженных системах обязаны быть **как можно короче**. Поэтому каждый отдельный HTTP-запрос выполняется в рамках своей собственной короткой физической транзакции БД.
- **Проблема потери обновлений (Lost Update):** Если пользователь в первом запросе (`GET`) считывает данные, а во втором запросе (`PUT`) отправляет измененные данные, за это время параллельный процесс (например, фоновый пакетный обработчик) может изменить ту же самую запись. Поскольку физическая транзакция первого запроса уже завершена, даже самый строгий уровень изоляции БД не сможет защитить от перезаписи чужих данных и возникновения аномалии **Lost Update**.

---

### **2. Сохранение контекста (Stateful vs Stateless)**

Протокол HTTP по своей природе не сохраняет состояние (stateless). Однако транзакции уровня приложения не могут быть полностью stateless, иначе новый запрос не сможет продолжить работу с того состояния, на котором остановился предыдущий:

- Сохранение состояния между веб-запросами формирует контекст диалога (conversational context) и обеспечивает **повторяемость чтений на уровне приложения (application-level repeatable reads)**.
- Для этого в JPA используются либо сохранение контекста постоянства между запросами (Extended Persistence Context), либо отсоединенные сущности (Detached Entities)[5][6].
- Однако одной только повторяемости чтений недостаточно: если состояние записи изменилось в БД параллельным процессом, сохранение отсоединенного снимка все равно приведет к потере обновления[7][8]. Для предотвращения конфликтов требуется механизм управления конкурентным доступом на уровне приложения[8].

### **3. Механизмы координации: Оптимистическая и пессимистическая блокировки**

Для координации изменений в транзакциях уровня приложения используются два подхода[9]:

#### **А. Оптимистическая блокировка (Optimistic Concurrency Control)**

Оптимистический подход исходит из предположения, что конфликты происходят редко, поэтому строки в БД физически не блокируются[10][11]:

1. **Версионирование сущностей:** Каждой строке в таблице сопоставляется версия (например, числовой атрибут `@Version`), которая монотонно увеличивается[11][12].
2. **Чтение:** При первом запросе клиент загружает сущность вместе с текущим значением версии (например, `version = 1`)[12].
3. **Модификация:** Во втором запросе при сохранении выполняется `UPDATE`, в котором текущая версия проверяется в условии `WHERE`[12][13]:

```
UPDATE product
SET quantity = 4, version = 2
WHERE id = 1 AND version = 1;

```

1. **Обнаружение конфликта:** Если за время между запросами запись уже была изменена другим процессом, ее версия в БД изменилась[13][14]. Количество обновленных строк будет равно нулю (`update count == 0`)[13][15].
2. Приложение фиксирует нулевой `update count`, выбрасывает исключение `OptimisticLockException` и прерывает транзакцию, защищая систему от потери данных[15].

> **Важно:** Для версий необходимо использовать **числовые значения**, а не временные метки (timestamps)[16][17]. Системное время не всегда возрастает строго монотонно (из-за сетевой синхронизации времени NTP оно может сдвигаться назад) и имеет разную точность в различных СУБД[16].

#### **Б. Пессимистическая блокировка (Pessimistic Locking)**

Пессимистическая блокировка строится на предположении, что конфликты неизбежны, и использует явные блокировки БД (`SELECT FOR UPDATE`)[9].

- В транзакциях уровня приложения монопольную блокировку (`exclusive lock`) применяют **только внутри последней короткой физической транзакции БД** многошагового процесса[10].
- Это гарантирует, что в момент финальной проверки и применения изменений никакая другая транзакция не сможет вмешаться в изменяемые ресурсы[10].
