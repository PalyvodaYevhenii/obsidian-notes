**Undo log** и **Redo log** — это два фундаментальных механизма низкоуровневого журналирования в реляционных СУБД, которые отвечают за обеспечение свойств **Atomicity (Атомарность)**, **Isolation (Изоляция)** и **Durability (Надежность)**.

---

### **1. Undo Log (Журнал отмены)**

**Undo log** фиксирует состояние данных **до** применения изменений (так называемый _before image_).

- **Для чего нужен:**
    1. **Откат транзакций (Atomicity):** Если в процессе транзакции произошла ошибка или вызван `ROLLBACK`, база данных с помощью записей undo восстанавливает исходные значения измененных строк к состоянию до начала транзакции.
    2. **Многоверсионность (MVCC / Isolation):** В системах с MVCC читающие запросы не блокируют пишущие. Когда транзакция изменяет строку, параллельные читатели видят предыдущую закоммиченную версию этой строки, которая на лету реконструируется из undo-сегментов.
- **Как реализован в СУБД:**
    - **Oracle:** Хранит старые версии данных в сегментах отката (**undo segments**) внутри `undo tablespace`.
    - **MySQL (InnoDB):** Сохраняет записи в **rollback segment** системного табличного пространства, разделяя их на данные для отката и данные для построения снимков MVCC. Фоновый поток (_purge thread_) очищает устаревшие undo-сегменты, когда они больше не нужны активным транзакциям.
    - **SQL Server:** При включении версионирования сохраняет старые версии строк в хранилище версий (`version store`) в базе `tempdb`, а очистку выполняет задача _Ghost cleanup_.
    - **PostgreSQL:** Не использует отдельный append-only undo log — вместо этого старые и новые версии строк хранятся прямо в основных страницах таблиц (с атрибутами `xmin` и `xmax`), а сборку мусора выполняет фоновый процесс `VACUUM`.

---

### **2. Redo Log / Write-Ahead Log (Журнал повтора)**

**Redo log** (в PostgreSQL называется **WAL — Write-Ahead Log**) — это последовательная (append-only) структура на диске, в которую записываются все изменения данных и индексов.

- **Для чего нужен:**
    1. **Надежность (Durability):** Сбрасывать измененные страницы таблиц и индексов из памяти на диск при каждом коммите слишком медленно (это создавало бы дорогостоящий случайный I/O). Вместо этого при коммите СУБД гарантированно сохраняет изменения в последовательный redo log.
    2. **Восстановление после сбоев (Crash Recovery):** Если сервер аварийно перезагрузится или отключится питание, данные в оперативной памяти (буферном пуле) будут утеряны, но СУБД восстановит актуальное состояние закоммиченных транзакций, «проиграв» записи из redo/WAL журнала.
- **Как реализован в СУБД:**
    - Изменения накапливаются в буфере лога в оперативной памяти и по умолчанию синхронно сбрасываются на диск при выполнении команды `COMMIT` перед возвратом управления клиенту.

---

### **Главные отличия:**

| Параметр           | Undo Log                                                                                    | Redo Log (WAL)                                                               |
| ------------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Что содержит**   | Состояние данных **до** изменений (_before image_)                                          | Сами изменения / векторы изменений (_delta_)                                 |
| **Основная цель**  | Откат изменений (`ROLLBACK`) и построение снимков в MVCC                                    | Восстановление закоммиченных данных при сбое (Crash Recovery)                |
| **Свойство ACID**  | **Atomicity** и **Isolation**                                                               | **Durability**                                                               |
| **Жизненный цикл** | Нужен только пока активны транзакции, которым требуются старые версии, после чего очищается | Хранится до фиксации страниц данных на диск (контрольной точки / checkpoint) |
