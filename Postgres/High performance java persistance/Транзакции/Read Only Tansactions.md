В **PostgreSQL** read-only транзакции используются для оптимизации выполнения читающих запросов, защиты от нежелательных изменений и маршрутизации трафика на реплики.

#### **1. Строгий запрет на изменение данных**

Если для соединения или транзакции установлен статус `read-only` (например, через JDBC-метод `connection.setReadOnly(true)` или SQL-команду `SET TRANSACTION READ ONLY`), PostgreSQL жестко блокирует любые попытки выполнения модифицирующих DML-операций (`INSERT`, `UPDATE`, `DELETE`), выбрасывая исключение.

### **2. Оптимизация уровня изоляции Serializable (Deferrable Snapshots)**

- **Проблема обычных Serializable-транзакций:** При использовании уровня `Serializable` в PostgreSQL механизм SSI (Serializable Snapshot Isolation) может приводить к ложным отменам транзакций (false-positive aborts) из-за потенциальных аномалий сериализуемости.
- **Решение via Deferrable Snapshots:** Для read-only транзакций PostgreSQL поддерживает специальный режим **SET TRANSACTION SERIALIZABLE READ ONLY DEFERRABLE**.
- **Принцип работы:** Транзакция приостанавливается и ожидает момента, когда база данных сформирует «безопасный снимок» данных (safe snapshot). Как только этот снимок доступен, транзакция выполняется с гарантией того, что она не будет отменена из-за конфликтов сериализуемости.
- **Применение:** Это наилучший выбор для длительных аналитических запросов и формирования отчетов над большими объемами данныx.

### **3. Маршрутизация трафика в Master-Slave репликации**

- В топологиях репликации Master-Slave узел-Slave принимает только read-only транзакции, что позволяет разгрузить Master-сервер от читающего трафика.
- JDBC-драйвер PostgreSQL предоставляет параметры подключения `targetServerType` (со значениями `master` или `preferSlave`) и `loadBalanceHosts` для балансировки соединений.
- Для полноценного разделения трафика на уровне приложения обычно настраивается маршрутизирующий `DataSource`, передающий read-only транзакции на отдельный пул подключений к репликам
