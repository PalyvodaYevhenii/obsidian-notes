### Lost Update 

#### Оптимистичные блокировки

Этот подход предполагает, что конфликты случаются редко. Проверка целостности происходит только в момент записи (коммита), а при обнаружении конфликта выбрасывается `OptimisticLockException` (требуется механизм повторных попыток — Retry).

- **По полю версии (`@Version`):** стандартный и самый быстрый способ. Hibernate добавляет в `UPDATE` проверку `WHERE id = ? AND version = ?` и увеличивает версию на 1. Подходит для 95% задач.
- **По изменённым полям (`@OptimisticLocking(type = DIRTY)` + `@DynamicUpdate`):** не требует колонки версии. В блок `WHERE` попадают старые значения только тех колонок, которые изменились в текущей транзакции. Позволяет разным потокам безопасно менять непересекающиеся поля одной строки.
- **По всем полям (`@OptimisticLocking(type = ALL)`):** не требует колонки версии. В блок `WHERE` добавляются старые значения абсолютно всех полей сущности. Используется редко, только для legacy-таблиц, где нельзя добавить `version`, но нужна защита всей строки целиком.
- **С явной проверкой при чтении или принудительным инкрементом (`LockModeType.OPTIMISTIC` / `OPTIMISTIC_FORCE_INCREMENT`):** используется в связке с `@Version`, когда нужно гарантировать, что прочитанные данные не изменились к концу транзакции, либо когда нужно обновить версию родителя при изменении его дочерних коллекций.

#### Пессимистичные блокировки (блокировка на уровне СУБД)

Этот подход используется при высокой конкуренции за одни и те же строки, когда повторные попытки (Retry) обходятся слишком дорого. Потоки выстраиваются в очередь на уровне базы данных.

- **Эксклюзивная блокировка (`LockModeType.PESSIMISTIC_WRITE`):** транслируется в `SELECT ... FOR UPDATE`. Никто другой не может изменить или заблокировать строку до завершения текущей транзакции. Идеально для списания баланса и бронирования остатков.
- **Разделяемая блокировка (`LockModeType.PESSIMISTIC_READ`):** транслируется в `SELECT ... FOR SHARE`. Другие транзакции могут читать строку, но не могут её изменять, пока удерживается блокировка.
- **Пессимистичная с инкрементом версии (`LockModeType.PESSIMISTIC_FORCE_INCREMENT`):** ставит `FOR UPDATE` и дополнительно увеличивает `@Version`. Нужна, если одна часть системы работает через пессимистичные блокировки, а другая — через оптимистичные.

#### Альтернативные подходы на уровне БД (без загрузки сущности в память)

Иногда проблему Lost Update проще и эффективнее решить средствами самой СУБД, минуя стандартный цикл «прочитать сущность -> изменить в Java -> сохранить».

- **Атомарные `UPDATE`-запросы (JPQL / Native SQL):** вместо чтения баланса в память и перезаписи выполняется прямой запрос вида `UPDATE Account a SET a.balance = a.balance - :amount WHERE a.id = :id AND a.balance >= :amount`. База данных сама гарантирует атомарность и защищает от потерянного обновления.
- **Строгие уровни изоляции транзакций (`REPEATABLE_READ` / `SERIALIZABLE`):** на уровне СУБД (например, в PostgreSQL на уровне `REPEATABLE_READ`) база сама отследит, что строка была изменена параллельной транзакцией, и прервёт вторую транзакцию с ошибкой сериализации (`could not serialize access due to concurrent update`).
