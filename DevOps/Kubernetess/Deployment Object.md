**Deployment** — основной объект в Kubernetes для управления stateless-приложениями (без хранения состояния внутри пода). Он не управляет подами напрямую: вместо этого он создаёт и контролирует **ReplicaSet**, который уже следит за точным количеством работающих подов.

### Что делает Deployment

- **Самовосстановление:** если под упал или нода вышла из строя, ReplicaSet автоматически поднимает замену.
- **Масштабирование:** достаточно изменить число в `replicas` (или подключить HPA), чтобы увеличить или уменьшить количество копий приложения.
- **Обновления без простоя (Rolling Update):** при смене версии образа Deployment создаёт новый ReplicaSet, постепенно поднимает новые поды и гасит старые.
- **Откат (Rollback):** старые ReplicaSet сохраняются в истории с нулём реплик, поэтому при баге можно одной командой вернуться на предыдущую ревизию.

### Минимальный YAML-манифест

YAML

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-api
spec:
  replicas: 3                     # Сколько копий пода держать запущенными
  selector:
    matchLabels:
      app: backend-api            # По каким меткам искать «свои» поды
  strategy:
    type: RollingUpdate           # Стратегия обновления по умолчанию
  template:                       # Шаблон, по которому создаются поды
    metadata:
      labels:
        app: backend-api          # Должно совпадать с selector.matchLabels
    spec:
      containers:
        - name: api
          image: my-registry/backend-api:1.2.0
          ports:
            - containerPort: 8080
```

### Основные команды

- `kubectl apply -f deployment.yaml` — создать или обновить Deployment.
    
- `kubectl rollout status deployment/backend-api` — отслеживать ход выкатки.
    
- `kubectl rollout undo deployment/backend-api` — откатиться к предыдущей версии.
    
- `kubectl scale deployment/backend-api --replicas=5` — быстро изменить число подов.
  

### Scaling 

**Масштабирование (Scaling) в Kubernetes** — это изменение количества ресурсов или копий приложения под текущую нагрузку. Оно работает на двух уровнях: **подов** (приложения) и **нод** (инфраструктуры), и бывает ручным или автоматическим.

### 1. Ручное масштабирование

Используется для быстрой проверки или предсказуемых нагрузок — вы просто меняете число реплик у `Deployment`, `ReplicaSet` или `StatefulSet`:

- Командой: `kubectl scale deployment/backend-api --replicas=5`
- Или изменением поля `spec.replicas` в YAML-манифесте с последующим `kubectl apply`.

### 2. Автоматическое масштабирование (3 главных механизма)

|**Механизм**|**Что масштабирует**|**Как работает**|**Когда использовать**|
|---|---|---|---|
|**HPA** _(Horizontal Pod Autoscaler)_|Количество подов (горизонтально)|Увеличивает или уменьшает `replicas` на основе CPU, RAM или кастомных метрик (RPS, длина очереди).|Stateless-приложения (бэкенд-сервисы, API, воркеры). Основной инструмент в проде.|
|**VPA** _(Vertical Pod Autoscaler)_|Ресурсы одного пода (вертикально)|Автоматически подбирает и меняет `requests`/`limits` по CPU и памяти (обычно с пересозданием пода).|Stateful-приложения (БД, кэши) или сервисы, которые нельзя размножить горизонтально.|
|**Cluster Autoscaler** _(или Karpenter)_|Количество нод в кластере|Если новые поды застряли в статусе `Pending` из-за нехватки места, заказывает новые виртуальные машины в облаке. Когда ноды простаивают — удаляет их.|Облачные кластеры (EKS, GKE, AKS) для автоматического расширения железа|
