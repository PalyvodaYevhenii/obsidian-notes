Это платформа для упраления, масштабирования и развертывания контейнеров.

- Контейнер может закрешится и его нужно заменить.
- Расширение или урезание контейнеров при изменении нагрузки
- Менеджинг трафика который идет к контейнеам

Главные задачи, которые решает Kubernetes

- **Автоматическое масштабирование:** если нагрузка на сайт растет, система сама добавляет новые копии (реплики) контейнера. Когда нагрузка падает — убирает лишние.
- **Самовосстановление (Resilience):** если какой-то контейнер «упал» или завис, Kubernetes мгновенно перезапускает его, а если вышел из строя целый сервер (нода) — переносит нагрузку на исправные машины.
- **Балансировка нагрузки:** равномерно распределяет входящие запросы между работающими контейнерами.
- **Декларативный подход:** вы описываете желаемое состояние системы (например: «должно работать ровно 5 копий этого сервиса»), а Kubernetes постоянно следит, чтобы реальное положение дел соответствовало этому правилу.
- **Безотказные обновления (Rolling Updates):** позволяет выкатывать новые версии приложения постепенно, по одному контейнеру за раз, без остановки всего сервиса.

### Объекты в Kubernetes

**Объекты в Kubernetes** — это постоянные сущности в системе, которые описывают **желаемое состояние** вашего кластера: какие приложения должны быть запущены, сколько их копий нужно, какие ресурсы им выделить и как они должны общаться по сети.

### Как они устроены

Вы описываете объект в виде манифеста (обычно в формате YAML) и отправляете его в Kubernetes API. У большинства объектов есть два ключевых блока:

- **`spec` (спецификация)** — то, чего вы хотите (желаемое состояние).
    
- **`status` (статус)** — то, что происходит на самом деле (обновляется самим кластером).
    

Kubernetes непрерывно сравнивает `status` со `spec` и автоматически исправляет расхождения (например, перезапускает упавший контейнер).

### Основные виды объектов

| **Объект**             | **За что отвечает**                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| **Pod**                | Минимальная единица развёртывания; обёртка вокруг одного или нескольких контейнеров.             |
| **Deployment**         | Управляет подами: следит за их количеством, перезапускает при сбоях, делает обновления и откаты. |
| **Service**            | Даёт постоянный внутренний IP/DNS и балансирует трафик между группой подов.                      |
| **Ingress**            | Маршрутизирует внешний HTTP/HTTPS-трафик к нужным сервисам внутри кластера.                      |
| **ConfigMap / Secret** | Хранят настройки и секреты (пароли, ключи, токены) отдельно от кода приложений.                  |
| **PV / PVC**           | Управляют постоянным хранилищем данных, которое сохраняется после удаления подов.                |
| **Namespace**          | Логически разделяет один кластер на изолированные среды (например, `dev`, `staging`, `prod`).    |

### Кластер **Kubernetes**

Кластер **Kubernetes** делится на две основные части: ==**Control Plane** (плоскость управления, принимающая глобальные решения) и **Worker Nodes** (рабочие узлы, на которых запускаются сами приложения)==.

---

1. Компоненты Control Plane (Мастер-узлы)

Отвечают за управление состоянием всего кластера и реакцию на события.

|Компонент|Роль и задачи|
|---|---|
|**kube-apiserver**|Единая точка входа в кластер. Принимает REST-запросы (например, от `kubectl`), проверяет права и обновляет данные в `etcd`.|
|**etcd**|Распределённое хранилище «ключ-значение». Хранит всю конфигурацию, секреты и текущее состояние кластера.|
|**kube-scheduler**|Планировщик. Следит за новыми подами без назначенного узла и выбирает для них оптимальную ноду на основе ресурсов и правил.|
|**kube-controller-manager**|Запускает фоновые контроллеры (Node, ReplicaSet, Endpoints и др.), которые приводят текущее состояние кластера к желаемому.|
|**cloud-controller-manager**|Связывает кластер с API облачного провайдера (создаёт балансировщики нагрузки, диски и маршруты в AWS, GCP, Azure и др.).|

---

2. Компоненты Worker Node (Рабочие узлы)

Работают на каждой машине в кластере и обеспечивают выполнение контейнеров.

- **kubelet** — главный агент узла. Следит за тем, чтобы контейнеры, описанные в `PodSpec`, были запущены и оставались здоровыми.
- **kube-proxy** — сетевой прокси. Поддерживает сетевые правила на узлах, обеспечивая связь между подами внутри кластера и доступ к ним снаружи через объекты `Service`.
- **Container Runtime** — среда выполнения контейнеров (например, _containerd_ или _CRI-O_), которая непосредственно скачивает образы и запускает контейнеры.
